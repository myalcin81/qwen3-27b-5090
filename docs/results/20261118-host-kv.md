# Host KV capacity and replay validation

This is a separate native Linux evaluation of the optional host KV tier. It does not use the
WSL2/400 W conditions of the older upstream throughput tables. The current forward-order acceptance
run is still in progress; the reverse-order diagnostic below is complete.

## Conditions

| Item | Value |
| --- | --- |
| GPU | RTX 5090, 32,607 MiB, configured power limit 600 W |
| System | Native Debian, kernel 6.12.101+deb13-amd64, NVIDIA driver 610.57.04, about 123 GiB host RAM |
| Weights | `juzbox/Qwen3.8-27B-NVFP4-GDN`, revision `3e686408cf61c2b579c67ab21696c9fc94e41e25`, operator chat template |
| Engine | NVFP4 KV, DSpine, host vision, `MAX_SEQS=8`, context limit 262,144 |
| GPU budget | `VRAM_MARGIN_GIB=0.25`, pool 674,816 tokens |
| Workload | 40 captured agent requests, two concurrent requests, up to 16,000 generated tokens each |
| Input size | 3,073,856 tokens per round; minimum 12,739, median 76,976, maximum 141,352 |
| Unique prefix union | 2,937,852 tokens, approximately 50.4 GiB of NVFP4 KV |
| Sampling | Captured requests and server defaults preserved; output is sampled, not required to repeat verbatim |

The request corpus contains private conversation data and is not published. Therefore the aggregate
results are a deployment acceptance record, not a fully public reproducible benchmark. Deterministic
storage correctness is checked separately by the repository's GPU fixtures.

## Correctness and capacity diagnosis

TT-8 passed all seven combinations of state retention, parked-prefill, host-KV and prefix-cache
fixtures. TT-11 reran the host-KV byte/token fixture and passed all four cases. Plain/speculative
decoding, full/partial pages and parked sequences are covered. The later main integration changes
frontend tool grammar code, not the native engine: commits `43f878d` and `9430f8a` have the same
`engine` tree, `2ffa20a06501ceaf794836b64f42b93022f63ebf`.

The original capacity estimate incorrectly divided the `reusable` counter by all four replay rounds.
Unseen cold prefixes contribute little to that counter. Counting the actual input token sequences
produced the 2.94M-token union above. Generated continuations, parked/active sequences and temporary
restore copies also need capacity; GPU plus 40 GiB of host KV leaves insufficient headroom here.

With `STATE_HOST_CACHE=32`, `KV_HOST_CACHE=40` and diagnostic inventory enabled, TT-11 observed zero
unreferenced host pages in all 228 snapshots. Checkpoint host pages equaled live host pages throughout.
End-of-round excess full pages were 266 and 153 out of roughly 46.8k physical pages; the transient peak
was 2,355. These observations do not support a large persistent duplicate-storage or orphan-page
problem in this run. Both tiers filled and host eviction occurred.

## Replay comparisons

The acceptance thresholds remain warm TTFT median <=2 s, cached/reusable >=60%, median per-request
decode >=200 tok/s and no transport/engine errors. Changing request order or memory budget is reported
explicitly; a diagnostic pass does not turn a failing configuration into a pass.

| Run | State / host KV (GiB) | Replay order | Inventory | Warm TTFT median / p90 | Cached / reusable | Decode median |
| --- | --- | --- | --- | --- | --- | --- |
| TT-8 | 32 / 40 | Forward, 40 x 4 | Off | 7.15 / 16.8 s | 10.5% | 193.7 tok/s |
| TT-11 | 32 / 40 | Forward, 40 x 2 | On | 8.00 s / not recorded | 169,280 / 3,073,816 = 5.5% | 206.7 tok/s |
| TT-12 | 32 / 40 | Cold forward, then reverse | On | 0.20 / 3.3 s | 2,702,336 / 2,908,551 = 92.91% | 230.0 tok/s |
| TT-13 | 32 / 56 | Forward, 40 x 4 | Off | Pending | Pending | Pending |

TT-12 ran on `43f878d` with library SHA-256
`19491444d81b89ac1e5b63759f5e1a8d69541244afbe74f1b936ef8c1df6543f`.
Its cold round had median TTFT 7.85 s and decode 210.65 tok/s. The reverse replay also reused **87.91%
of all prompt tokens**, independently of the `reusable` denominator. Reverse ordering interacts with
the scheduler's bounded history, so that denominator is smaller than in the forward runs.

All 80 TT-12 requests completed without HTTP/engine errors. Each round had one thought-only
max-token truncation, recorded separately from engine failures. No host allocation failures or
unreferenced host pages were observed; the reverse round still performed 108 host evictions.
The restored original engine reported matching settings and healthy status. The improvement when
reading recent prefixes first supports capacity plus cyclic LRU pressure, rather than a broken
lookup/restore path.

TT-13 tests integrated head `9430f8a`, with the same native library, in a separate process. It increases
only the host KV budget from 40 to 56 GiB and disables diagnostic scans for the final performance
measurement. State memory remains 32 GiB; strict tools remain off. It preserves the original request
order and runs one cold plus three warm rounds. No permanent production settings are changed.

## Validation boundary

The combined frontend/CPU ASan/UBSan suite passed 473 tests with 16 existing environment skips.
CPU and CUDA CI passed on `9430f8a`. GPU parity fixtures establish the tested storage correctness;
they do not prove performance for arbitrary workloads. RAM capacity must cover the actual working
set and restore/continuation headroom. `KV_HOST_CACHE` remains opt-in and defaults to zero.
